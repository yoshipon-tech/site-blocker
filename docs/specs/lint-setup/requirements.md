# 要件: lint-setup

## 目的

型の誤りや書式の揺れ、ワークフローの書き間違いを、実行やレビューの前に機械で見つけたい。現状はテスト（Vitest）しかなく、型チェックも lint もフォーマッタもない。
後続の `blocked-page` `redirect-rules` が分岐する前に、全アプリ共通の静的解析を main で確定させる。

## 要件

### 1. 型チェック

- **1.1** 開発者がリポジトリ直下で型チェックを実行したとき、システムは全アプリのソースとテストを型チェックしなければならない
- **1.2** 型の誤りがあるとき、システムは終了コード 0 以外で終了し、ファイル名と行番号を表示しなければならない
- **1.3** 型が暗黙に any になる箇所と、null になりうる値を確かめずに使う箇所があるとき、システムはそれを型の誤りとして扱わなければならない
- **1.4** 開発者がアプリを指定して型チェックを実行したとき、システムはそのアプリだけを型チェックしなければならない

### 2. lint

- **2.1** 開発者がリポジトリ直下で lint を実行したとき、システムは全アプリのソースとテストを検査しなければならない
- **2.2** 違反があるとき、システムは終了コード 0 以外で終了し、ファイル名・行番号・ルール名を表示しなければならない
- **2.3** React のフックの呼び出し規則に反するコードや、フックの依存の漏れがあるとき、システムはそれを違反として扱わなければならない
- **2.4** ビルド成果物・依存パッケージ・ツールが生成したファイルは、システムは検査の対象にしてはならない

### 3. フォーマット

- **3.1** 開発者がフォーマットの確認を実行したとき、書式が揃っていないファイルがあれば、システムは終了コード 0 以外で終了し、そのファイル名を表示しなければならない
- **3.2** 開発者がフォーマットを実行したとき、システムは対象ファイルを書き換えて書式を揃えなければならない
- **3.3** 書式の規則と lint の規則が矛盾するとき、システムはフォーマット後のコードを lint 違反にしてはならない
- **3.4** フォーマットの確認と実行のとき、システムは Markdown ファイルを対象にしてはならない

### 4. ワークフローの検査

- **4.1** 開発者がワークフローの検査を実行したとき、システムは `.github/workflows/` 配下の全ワークフローを検査し、誤りがあれば終了コード 0 以外で終了しなければならない
- **4.2** 開発者が新しい環境でツールを導入したとき、システムはワークフローの検査ツールを、リポジトリで固定したバージョンで導入しなければならない

### 5. 一括実行

- **5.1** 開発者がリポジトリ直下で一括チェックを実行したとき、システムは型チェック・lint・フォーマットの確認・ワークフローの検査・テストをすべて実行しなければならない
- **5.2** いずれかが失敗したとき、システムは終了コード 0 以外で終了し、どの検査が失敗したか分かる出力を表示しなければならない

### 6. push 前の自動実行

- **6.1** 開発者が `git push` を実行したとき、システムは push の前に一括チェックを自動で実行しなければならない
- **6.2** 一括チェックが失敗したとき、システムは push を中止しなければならない
- **6.3** 開発者がリポジトリ直下で依存関係をインストールしたとき、システムは追加の手順なしに 6.1 の自動実行を有効にしなければならない
- **6.4** Node.js・pnpm がシェルの PATH にない環境（エディタの Git 画面など）から push したときも、システムはリポジトリで固定したバージョンで一括チェックを実行しなければならない
- **6.5** 作業ルールの文書は、push 前に一括チェックを自動実行すること、コミットメッセージの検査と CI は行わないことを記載していなければならない

### 7. 既存コード

- **7.1** この機能の完了時点で、main の既存コードは 1〜5 のすべての検査を通らなければならない

## 範囲外

- プルリクや push をきっかけに GitHub 上で検査を走らせる CI — push 前のローカル実行で足りるとした（U1）
- コミット時の自動実行・コミットメッセージの検査 — push 前の1か所に絞る
- Markdown のフォーマット — 表の整形が一斉に変わるため（U2）
- エディタの設定（保存時の自動フォーマットなど） — 個人の環境に任せる
- E2E テスト（Playwright） — `blocked-page` で入れる
- 公開ワークフローから検査を呼ぶこと — `blocked-page` の公開ワークフローで行う
- 拡張と Web で共有するコードの置き場所（`packages/`） — 設定ファイルはコードではないので、ルートに置く想定で足りる
