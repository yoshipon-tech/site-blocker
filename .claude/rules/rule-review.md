# レビュールール

レビュー指摘を書くときに守ること。人が書く指摘でも、`review` スキルが出す指摘でも同じ形式にする。

## 指摘の形式

`<修正要否> (<観点>): <指摘>` の形にする。

```
MUST (Functionality): hash が空のとき元URL欄に "undefined" が出る。空なら欄ごと出さない
Q (Design): ここで正規表現ルールにしているのは、サブドメインもまとめて止めるため？
```

## 修正要否

| 修正要否 | 意味                                                                     | 修正 |
| -------- | ------------------------------------------------------------------------ | ---- |
| `MUST`   | 直さないとマージできない。バグ、仕様との不一致、セキュリティ、壊れる設計 | 必須 |
| `SHOULD` | 直したほうがよい。直さないなら返信で理由を書く                           | 推奨 |
| `BETTER` | こうするともっとよい。今でなくてもよい                                   | 任意 |
| `NITS`   | 些細な指摘。誤字、細かい表記ゆれ                                         | 任意 |
| `IMO`    | 個人の意見・好み。従わなくてよい                                         | 任意 |
| `Q`      | 質問。意図が読めないので聞いている                                       | 不要 |
| `FYI`    | 参考情報の共有。指摘ではない                                             | 不要 |

## 観点

指摘を書く前に、それがどの観点の話なのかを決める。観点を言えない指摘は、好みの表明であってレビューではない。

| 観点            | 見るもの                                                             | 指摘の例                                         |
| --------------- | -------------------------------------------------------------------- | ------------------------------------------------ |
| `Design`        | 責務の置き場所、依存の向き、あとから変えたときに壊れないか           | 拡張側に表示の責務が入っている                   |
| `Simplicity`    | 同じ結果をより少ない要素で書けないか、不要な抽象や分岐がないか       | 分岐がネストしているが早期 return で平らにできる |
| `Naming`        | 名前と中身が一致しているか、同じ概念に別の名前が使われていないか     | `url` が元URLなのかリダイレクト先なのか読めない  |
| `Style`         | 既存コードの書き方に揃っているか（フォーマッタが決めるものは対象外） | 周囲は関数宣言だがここだけアロー関数             |
| `Functionality` | 仕様どおりに動くか、境界・異常系が抜けていないか                     | hash が空のときの挙動が決まっていない            |
| `Test`          | 壊れたときに落ちるテストか、テストが仕様を説明しているか             | 実装を消してもテストが通る                       |
| `Document`      | 前提を知らない人が読んで分かるか、変更に合わせて更新されているか     | 契約を変えたのに `guide-tech.md` が古いまま      |

## 書き方

- **修正要否のないコメントを書かない。** 受け手が直すべきか判断できず、全部が「たぶん直したほうがいい」に見える
- **`MUST` には理由と直し方を書く。** 「ここが悪い」で止めない
- **好みを `MUST` や `SHOULD` にしない。** 理由が「そのほうが好き」なら `IMO`
- **読み違えの可能性があるなら `Q` から入る。** 前提を知らないだけのことがある
- **1つの指摘に1つの観点。** 複数にまたがるなら指摘を分ける
- **`Design` と `Functionality` を先に見る。** `Naming` や `Style` から潰すと、設計の議論が細かい指摘の数に埋もれる
- **フォーマッタや lint が機械的に直せるものは指摘しない。** 設定で直す
- **`MUST` が多いときは、指摘を並べる前に設計の相談に切り替える。** 個別に直しても収束しない

観点の表は「どこを見るか」を思い出すためのもの。チェックリストではないので、毎回すべてを埋める必要はない。

## `review` スキルとの対応

`review` スキルは `Critical` / `Important` / `Suggestion` / `FYI` で重大度を返す。レポートを読むときも人に伝えるときも、この表の語に置き換える。

| スキルの重大度           | 修正要否                                                |
| ------------------------ | ------------------------------------------------------- |
| `Critical` / `Important` | `MUST`                                                  |
| `Suggestion`             | `SHOULD` / `BETTER` / `NITS` / `IMO`（理由の強さで選ぶ） |
| `FYI`                    | `FYI`                                                   |

`REJECTED` になるのは `MUST` が1つ以上あるときだけ。`SHOULD` 以下だけなら通してよい。
