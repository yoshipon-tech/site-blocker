# spec

## 概要

1つの機能について `requirements` → `design` → `tasks` を順に作る。**各段を書き終えたら必ず停止し、人の確認を待つ。**確認なしに次の段へ進んではならない。

出力先は `docs/specs/<機能名>/` の3ファイル。

```
docs/specs/<機能名>/
├── requirements.md   何を満たすか
├── design.md         どう作るか
└── tasks.md          どう分けて作るか
```

## 引数

| 形 | 動作 |
| -- | ---- |
| `<機能名>` | 未作成の段から順に実行する |
| `<機能名> requirements` | その段だけ作り直す。後続の段が既にあれば、整合が崩れることを報告する |
| `<機能名> design` | 同上 |
| `<機能名> tasks` | 同上 |

## 開始前に必ずやること

1. `.claude/rules/guide-product.md` `guide-tech.md` `guide-structure.md` を読む。ここに書かれた前提に反する設計を提案しない
2. `docs/specs/` の既存機能を確認し、影響範囲（触るディレクトリ）が重ならないことを確かめる。重なるなら、そのまま進めず人に報告する
3. 既存の `docs/specs/<機能名>/` があれば読む。上書きではなく差分更新として扱う

## Phase 1: requirements

型は `templates/requirements.md`。

- EARS 形式（「〜のとき、システムは〜しなければならない」）で書く
- **実装手段を書かない。** ライブラリ名・ファイル名・API 名が出てきたら、それは design の内容
- 各要件は「できた / できていない」を機械か目視で判定できること。判定不能な語（適切に、使いやすい、高速に）を使わない
- 「範囲外」を必ず埋める。ここが空の要件は範囲が決まっていない
- 決まらないと design に進めない論点は「未決事項」に書き、**人に聞く**。勝手に決めない
- 80行以内。超えるなら機能の分割を提案する

書き終えたら停止し、次を報告する。

- 未決事項があれば、その一覧と、それぞれについての質問
- 範囲外にしたものと、その判断理由
- 判定が目視になる要件（機械判定できないもの）の一覧

## Phase 2: design

型は `templates/design.md`。`research.md` は作らない。調べた結果は「決定と理由」に畳み込む。

- requirements の全要件が、設計のどこかで扱われていること
- 「決定と理由」には**後から変えるのが高くつく選択だけ**を書く。却下した案とその理由を必ず添える
- 外部に出る契約（URL の形、メッセージの形、配布物に焼き込まれる値）は必ず「決定と理由」に入れ、「変えるときの影響」を書く
- 「他機能との境界」を必ず埋める。並行開発で衝突しないための宣言なので、空にしない
- **「検証方法」を必ず埋める。** 要件ごとに手段を割り当てる
  - `コマンド` — 終了コードで判定できるもの
  - `Playwright` — 回帰させたいもの。テストとしてコードに残る
  - `ブラウザ` — 見た目や実挙動の初回確認。証拠は残らないので、回帰が要るものに使わない
- 技術選定で調査が要る場合は WebSearch / WebFetch を使い、根拠の出典を「理由」に残す
- 150行以内

書き終えたら停止し、次を報告する。

- 決定した項目と、却下した案
- 調査して分かったことのうち、requirements の前提を覆すもの
- 「リスク」に挙げた前提

## Phase 3: tasks

型は `templates/tasks.md`。

- 1タスク = 受入基準1〜2個。実装とその検証がセットで終わる単位にする
- **`_検証:_` を全タスクに必ず書く。** design の「検証方法」から引く。書けないタスクは受入基準が判定可能になっていないので、requirements に戻る
- `_要件:_` で requirements の番号に紐づける。全要件がどれかのタスクに現れること
- `_範囲:_` に触るファイル・ディレクトリを書く。他タスクと重なるなら `_並行: 不可_` にして理由を書く（lockfile や共有設定の更新など）
- 順序は依存関係で決める。検証できない順序にしない（検証基盤を作るタスクを後ろに置かない）
- 100行以内

書き終えたら停止し、次を報告する。

- 要件とタスクの対応表（漏れがあれば明示）
- 並行不可にしたタスクとその理由
- ブラウザ検証になるタスク（人の目が要るもの）の一覧

## 禁止事項

- 段を飛ばさない。人の確認なしに次の段を書き始めない
- 未決事項を自分で決めて埋めない。聞く
- 分量上限を超えたまま「完了」と報告しない
- `docs/specs/<機能名>/` 以外にファイルを作らない
