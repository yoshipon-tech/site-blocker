# impl

## 概要

`docs/specs/<機能名>/tasks.md` のタスクを上から順に実装する。**タスクごとにコミットしない。**人の確認も挟まない。代わりに、タスクごとに `_検証:_` に書かれた検証を実際に実行する。

全タスクが終わったら通しでレビューし、**コミットせずに停止して人に返す。**コミットは人がやる。

## 引数

| 形 | 動作 |
| -- | ---- |
| `<機能名>` | 未完了タスクを上から全部 |
| `<機能名> 1.1 2.1` | 指定タスクだけ |

## 開始前に必ずやること

1. `docs/specs/<機能名>/` の3ファイルを読む。`tasks.md` が無ければ `/spec` を先に実行するよう報告して止まる
2. `.claude/rules/` の `guide-*.md` と `rule-git.md` を読む
3. `git status` を確認する。未コミットの変更があれば、どれが自分の作業範囲外かを把握してから始める
4. 作業ブランチを確認する。`main` にいる場合は、機能名のブランチを切るよう人に確認する

## タスクごとのループ

各タスクについて、この順で進める。

```
1. タスクの受入基準と _検証:_ と _範囲:_ を読む
2. 実装する（_範囲:_ の外のファイルを触らない）
3. _検証:_ を実際に実行する
4. 失敗 → 原因調査して修正 → 再検証（最大3回）
5. 成功 → tasks.md に [x] を付ける（コミットはしない）
6. 次のタスクへ
```

### 2. 実装

- `_範囲:_` に書かれたファイル・ディレクトリの外を変更しない。必要になったら、そのタスクの範囲設定が誤っているので止めて報告する
- 受入基準に書かれていないものを作らない

### 3. 検証

`_検証:_` の手段に従って**実際に実行する**。実行せずに「通るはず」と判断しない。

| 手段 | やること |
| ---- | -------- |
| コマンド | そのコマンドを実行し、終了コードと出力を確認する |
| Playwright | テストを書き、実行して通す。テストはコードとして残す |
| ブラウザ | chrome-devtools MCP で実際に開き、期待する見え方・挙動になっているか確認する |

#### 拡張（`apps/extension`）をブラウザ検証する手順

chrome-devtools MCP は既定で拡張を無効にして Chrome を起動するため、`--load-extension` では読み込めない。`install_extension` を使う。

```
1. apps/extension をビルドする（.output/chrome-mv3/ が出る）
2. install_extension に .output/chrome-mv3/ の絶対パスを渡す
3. list_extensions で読み込まれたこと（名前・ID・有効状態）を確認する
4. 検証対象の URL へ遷移する
5. 遷移後の URL と表示を確認する
6. コンソールのエラー有無を確認する
```

`--isolated=true` で起動するので、毎回まっさらなプロファイルになる。**拡張は毎セッション読み込み直しが要る。**人の普段の Chrome プロファイルは汚さない。

ブラウザ検証では、確認した内容（開いた URL、遷移先 URL、見えたもの、コンソールエラーの有無）を報告用に記録しておく。証拠が残らない手段なので、後でまとめて人に見せる。

### 4. 失敗時

1. `debug` スキルを呼ぶ。推測で直さず、原因から調べる
2. 修正して再検証する
3. **同じタスクで3回失敗したら、そこで停止して人に返す。**それまでに分かったこと（試した仮説と、否定された根拠）を報告する

3回のカウントは「検証が失敗した回数」で数える。実装のやり直しではなく検証の失敗回数。

### 5. 完了の記録

`tasks.md` の該当タスクを `[ ]` から `[x]` にする。**`git commit` は実行しない。**

## 全タスク完了後

1. `review` スキルで、実装全体を spec（requirements / design）に照らしてレビューする
2. `verify-completion` スキルで、完了の主張を新しい証拠で確認する
3. 人に報告して停止する

報告には次を含める。

- 実装したタスクの一覧と、各タスクの検証結果
- ブラウザ検証で確認した内容（証拠が残らないため、ここで言語化する）
- `review` で出た指摘と、対応したか見送ったか
- 変更したファイルの一覧（`git status`）
- 想定と違ったこと、spec と実装がずれた箇所

**コミットせずに止まる。**コミットとプルリクは人が `rule-git.md` に従ってやる。

## 並行開発

並行は**機能単位**。`redirect-rules` と `blocked-page` のように影響範囲が分かれている機能を、別の worktree で同時に進める。

```bash
git worktree add ../site-blocker-wt/<機能名> -b feat/<機能名>
cd ../site-blocker-wt/<機能名> && pnpm install
```

- worktree はこのスキルでは作らない。人が作る
- `tasks.md` の `_並行: 不可_` は**同一機能内のタスクの話**で、worktree の単位ではない。順序制約として扱う
- 共有するもの（`.claude/rules/`、spec、URL の契約、ルート設定）はブランチを切る前に `main` で確定させる

## 禁止事項

- `git commit` しない
- 検証を実行せずに完了扱いにしない
- `_範囲:_` の外を変更しない
- 3回失敗したタスクを、原因が分からないまま4回目に進めない
- tasks.md にないものを実装しない
