# work

## 概要

`issues/<issue名>.md` を作業指示書として実装する。**issue ファイルは読むだけで編集しない。**気づいたことは報告で返す。issue を書くのはメイン（`issue` スキル）の役割。

`impl` と違い、このスキルは**自分でコミットする**。その代わり、コミットの前に新しいコンテキストでレビューして指摘を直す。push と PR の作成は人がやる。

リポジトリ固有の手段（確認・レビュー・コミット・PR）は `issues/README.md` にある。開始前に必ず読む。

## 開始前に必ずやること

1. `issues/<issue名>.md` と `issues/README.md` を読む
2. `status: ready` であることを確認する。違えば始めずに人に返す
3. `git branch --show-current` が `main` でないことを確認する。`main` なら始めずに、worktree を作るよう人に返す
4. `git status` を確認する。未コミットの変更があれば、どれが自分の範囲外かを把握してから始める
5. issue が spec を参照していれば、その spec も読む

## 実装

- **範囲を守る。** issue の「触ってよいファイル」の外を変更しない。必要になったら、触る前に止まって AskUserQuestion で聞く
- **迷ったら聞く。** issue の「迷ったら」に書いてあること、解釈が分かれて成果物が変わることは、自分で決めず AskUserQuestion で聞く
- issue が spec の tasks を参照していれば、`impl` スキルでタスクを実装する。`impl` が止まったら、このスキルの「確認」に戻る
- 完了条件にないものを作らない

## 確認

- issue の「確認方法」と、`issues/README.md` の確認の手段を**実際に実行する**。「通るはず」で進めない
- 失敗したら `debug` スキルで原因から調べて直す。**同じ確認で3回失敗したら止まって人に返す**
- 完了条件を1つずつ、確かめた証拠（コマンドと結果、見たもの）と対応づけて控えておく

## レビュー

コミットの前に、**新しいコンテキスト（サブエージェント）でレビューする。**自分の実装を自分の文脈でレビューしない。

1. Agent ツールでサブエージェントを起動し、`issues/README.md` のレビューの手段を使わせる。渡すもの: issue ファイルのパス、差分の見方（`git diff`）、確認の結果
2. 修正必須の指摘を直し、確認をやり直す
3. 直さない指摘は、理由を報告に書く

## コミット

- `issues/README.md` のコミットの決まりに従う
- issue ファイルを含めない（編集していないはず。差分にあれば戻す）
- push はしない

## 報告

最後に次を書いて止まる。

- **要約**: 何を変えたか、迷って聞いたこと、確認して分かったこと（issue の「迷ったら」で報告を求められたものを含む）
- **完了条件**: 1つずつ、満たしたかと、その証拠
- **レビュー**: 出た指摘と、直したか見送ったか
- **次にやること**: issue に書き足したほうがよいこと、後続の issue の候補
- **push と PR 作成のコマンド**: `issues/README.md` の形で、**push と PR 作成を別の行に**書く。人がターミナルで1つずつ実行する（チャットの `!` には頼らない）

## 禁止事項

- issue ファイルを編集しない
- 範囲の外を、聞かずに変更しない
- 確認を実行せずに完了扱いにしない
- レビューを飛ばしてコミットしない
- push・PR の作成をしない
